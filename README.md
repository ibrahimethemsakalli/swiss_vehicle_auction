# AutoVeri.ch

Swiss vehicle auction application built with Next.js 14 App Router, TypeScript, Prisma/PostgreSQL, Tailwind CSS, shadcn-style Radix primitives, i18next and Socket.IO.

## Local preview

Run `pnpm install`, `pnpm db:generate`, and `pnpm dev`. Without DATABASE_URL, the application shows explicitly labelled fictional demo data. Demo mode never creates listings, authorizes money, or places bids. Sample galleries use 32 licensed real photographs across 12 galleries (2–4 different views of one physical vehicle per gallery). Files are served locally. Sources, authors, licences and modification notes are available at `/photo-credits`, beside each gallery image, and in `public/samples/PHOTO-CREDITS.md`. Models/variants and stated model years follow the photo sources; visible colours/body shapes follow the photos. Source year is separate from first registration. Unknown years, registration dates, equipment and technical data are not invented. Price, mileage, location and identifiers remain explicitly fictional test values.

Open http://localhost:3000. The custom server binds to loopback by default; set HOST intentionally for your deployment. Do not use `next start`: it does not attach Socket.IO.

For local records, run `pnpm db:local` in a separate terminal. It initializes persistent PostgreSQL on `127.0.0.1:55432`, creates `autoveri` and isolated `autoveri_test` databases, and creates `.env` with random database and NextAuth secrets only if that file does not already exist. Keep the terminal running; Ctrl+C stops PostgreSQL without deleting data. `.local/` and `.env` are ignored. The embedded runtime is for development; production should use a managed PostgreSQL instance with backups.

Then run `pnpm db:deploy`, `pnpm db:generate`, and `pnpm dev`. For an existing PostgreSQL server, configure DATABASE_URL in `.env` instead. Do not overwrite a generated `.env` with the example file: add the provider values to it. A configured but unavailable database produces an error, never substitute demo data.

## Account and provider setup

1. Open `/register`, choose private seller or dealer, enter an E.164 Swiss number (`+41…`) and a password of at least 12 characters, at most 72 UTF-8 bytes. Registration cannot assign ADMIN or verification flags. Passwords are hashed with bcrypt. Registration, login and SMS attempts use PostgreSQL rate limits.
2. Configure `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and `TWILIO_VERIFY_SERVICE_SID` from a Twilio Verify service in `.env`, then restart the application. `/verify` sends and checks SMS through Twilio. The destination always comes from the authenticated account. Codes are never stored. Trial-account destination restrictions still apply. No local universal code or runtime verification bypass is provided.
3. SMS verifies phone ownership only. Create your operator account, then explicitly grant its role with `pnpm admin:grant your-email@example.com --confirm`. This command changes only the role and records an audit event. In `/admin` → Identity reviews, approve other phone-verified accounts only after reviewing identity evidence outside the application, recording the evidence reference. Operators cannot approve themselves. Automated identity/document verification and an evidence-upload workflow are not included.
4. Configure matching Stripe **test** keys: `STRIPE_SECRET_KEY` and `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`. The public key is embedded in the frontend build, so rebuild after changing it. `STRIPE_ALLOW_LIVE=false` is the default; live keys require explicit opt-in. Card fields use Stripe Elements and are sent directly to Stripe.
5. Configure the signed webhook at `/api/payments/webhook` for `payment_intent.amount_capturable_updated`, `payment_intent.canceled`, `payment_intent.payment_failed` and `payment_intent.succeeded`. Locally, use `stripe listen --forward-to localhost:3000/api/payments/webhook`, put its signing secret in `STRIPE_WEBHOOK_SECRET`, then restart. In production use your HTTPS endpoint's own signing secret.
6. A verified seller uploads photos and submits `/sell`; an admin approves the listing to start a full seven-day auction. A different verified user opens the vehicle, authorizes CHF 30, and separately confirms the binding bid. The server retrieves Stripe state before accepting the bid. Being outbid queues cancellation; the custom server processes releases every 15 seconds with durable retries.

The integration requests `capture_method=manual`, exactly 3000 centimes in CHF, with card payments allowed. It validates intent ownership, metadata, currency, amount, capturable amount and Stripe's `capture_before` timestamp. It never assumes a seven-day bank authorization. Active bidders and winners with unresolved settlements can renew near-expiry holds from their dashboard; the old hold is released after replacement. Unused checkouts are canceled after 15 minutes. TWINT/Datatrans are not implemented.

## Auction closing and settlement

The custom server checks due auctions every 15 seconds and catches up after restarts. Closing locks the same vehicle row as bidding, rechecks the database clock and extended deadline, and creates at most one settlement per vehicle. The highest active bid wins only if it meets the reserve; equal amounts are ordered by earliest bid, then ID. No bids or a missed reserve produces no sale and queues all remaining holds for release. Other unused holds are released when a winner is selected. Public Socket.IO updates include the closed status. The vehicle uses `EXPIRED` while bidding is closed; its separate settlement records whether a sale is pending. Only a confirmed fee capture changes it to `SOLD`.

Open **Sale settlements** in `/dashboard` or `/admin`:

- The seller confirms that vehicle handover and payment of the vehicle price have completed. This queues a CHF 30 `CAPTURE_FEE`, with explicit confirmation and an audit reason. The vehicle purchase price is paid outside this application.
- The seller can report buyer default. Reporting alone does not charge the buyer. An independent admin reviews the evidence reference, then dismisses the report, approves a CHF 30 `CAPTURE_COMPENSATION`, or cancels settlement and releases the hold. An admin who is the seller or buyer cannot adjudicate that sale. There is no automatic default deadline or penalty merely for elapsed time.
- Buyers see their winning settlements and can renew an expired/near-expiry authorization after auction end while the settlement is unresolved. Capture attempts require a valid authorization. An expired/canceled authorization becomes `PAYMENT_FAILED`; after renewal, an independent admin can retry the original outcome.
- Cancellation is blocked once capture is queued or confirmed. Completed sales and confirmed defaults are terminal. Participants can open disputes; actual refunds require an external operator workflow.

Settlement states are `AWAITING_CONFIRMATION`, `DEFAULT_REVIEW`, `CAPTURE_PENDING`, `COMPLETED`, `DEFAULTED`, `PAYMENT_FAILED`, and `CANCELLED`. Audit reasons and reviewer IDs are retained as private `settlement.action` events. Admins can see recent reasons in the settlement panel. Cancellation and payment release are separate statuses: a canceled sale can still show `RELEASE_PENDING` until Stripe confirms cancellation.

The durable capture worker uses leased jobs, exponential retry and a stable idempotency key per hold. It retrieves Stripe state before capture, sends exactly 3000 centimes and records a capture key in Stripe metadata. If Stripe succeeds but the response or database commit is lost, retries or signed webhooks recover the result without a second charge. Captured amount and metadata must match before recording `CAPTURED_FEE`/`CAPTURED_COMPENSATION`. An unrecognized external capture becomes `CAPTURED_UNEXPECTED` and requires manual investigation. Ambiguous provider/network failures remain pending; they are never represented as a completed sale. Keep the custom server running for closing, capture and release processing.

Compensation capture records funds on the platform's Stripe account; it does **not** transfer them to the seller. Seller payouts require a separate Stripe Connect or accounting workflow. Live capture testing still needs provider credentials. See [Stripe capture API](https://docs.stripe.com/api/payment_intents/capture).

Relevant provider references: [Stripe manual capture](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method), [Stripe webhooks](https://docs.stripe.com/webhooks), [Twilio Verify](https://www.twilio.com/docs/verify/api/verification), [Stripe allowed payment methods](https://support.stripe.com/questions/fix-the-payment-method-types-error).

## Backend connections

- `GET /api/market` and `/api/market/[id]`: public DTOs omit full VIN, reserve prices, passwords, phone numbers and bidder identities. Search accepts validated JSON `filters` and a `page`, applies filters in PostgreSQL and returns 24 vehicles plus `total` and make/model options. The former 200-record cutoff is removed. Price/deadline sorting currently sorts compact matching price records on the server before fetching the page's full records; move this ordering into SQL for very large catalogues. Favorites apply the same filter semantics locally, including closed listings.
- `GET /api/account`: authenticated, current-user-only dashboard data. `GET /api/holds?vehicleId=...`: current user's unused, valid CHF 30 authorization.
- `POST /api/register`, `GET/POST /api/verification`: account registration, authenticated phone verification and status. Missing providers fail closed.
- `GET/POST /api/admin/identities`: admin-only pending identity reviews and evidence-reference audit.
- `POST /api/payments/holds`: authenticated `create` / `confirm` actions, optional `replacementBidId` for an existing active bid. Authorization is established only from server-retrieved Stripe state. Client secrets are returned only to the owner and are not stored or logged.
- `POST /api/payments/webhook`: raw-body signature validation, event deduplication and retrieval of current provider state to handle out-of-order events. Unexpected captures are surfaced for review.
- `GET/POST /api/settlements`: authenticated buyer/seller visibility, admin review and audited settlement actions. Seller completion/default reports require ownership; financial default approval/cancellation/retry require an independent admin. Browser writes require same-origin requests.
- `POST /api/ocr/parse-fahrzeugausweis`: authenticated, phone-verified multipart `document` (JPEG/PNG, max. 5 MB). Set OCR_ENABLED=true. Results require human review. Documents and raw OCR text are not retained. First use downloads Tesseract language files.
- `POST /api/uploads`: verified sellers only, multipart `photo` (JPEG/PNG, max. 5 MB). Development stores public vehicle photos in ignored `.uploads`. Production requires an explicit durable UPLOAD_DIR. `GET /api/uploads/[id]` serves generated filenames with no-sniff headers. Move to object storage, image re-encoding, quotas and orphan cleanup before scaling. Never upload registration documents through the photo route.
- `POST /api/vehicles`: validated listing creation; pending verification. Admin approval resets start/end to a full seven days.
- `GET/POST /api/admin`: checks the authenticated database role and suspension status. Decisions lock the vehicle, validate the seller and log before/after fields, reviewer and reason as retained `admin.review` audit events. Audit events are never sent to public sockets.
- `POST /api/bids` or socket `auction.bid`: authenticated bid with `{vehicleId,holdId,requestId,amount:"12500.00"}`. Server validates authorization ownership, currency, value, expiry and single use. Bid writes lock the vehicle and hold. A bid in the last 180 seconds adds 120 seconds to the existing deadline.
- `auction.subscribe` sends an initial snapshot; `auction.updated` delivers committed price/deadline/version events. The UI rejects stale versions. Outbid releases are durably queued as Transaction records. Public broadcasts use an at-least-once outbox.
- Browser mutation APIs reject missing/foreign Origin headers. NextAuth protects its own sign-in flow.

## Explicitly unfinished integrations

The frontend exposes these states honestly; disabled controls never simulate a successful transaction:

- Live Twilio/Stripe activation and testing with account credentials. Provider adapters are implemented, but this workspace has no provider credentials configured.
- Automated identity/dealer registry validation, identity evidence intake, email verification and email-delivered recovery. Offline recovery codes and authenticated password changes are implemented.
- Datatrans/TWINT integration, refunds, chargeback handling and seller compensation payouts. Compensation capture does not transfer funds to the seller.
- Automated default deadlines and external financial resolution of disputes. Fixed-price offers and participant dispute intake/review are implemented; evidence review and refunds still require operator action.
- Production OCR job isolation, request/pixel/CPU limits, trusted-proxy IP throttling, upload quotas, object storage, multi-instance Socket.IO adapter/outbox fan-out, PostGIS search, notifications and PWA support. Current registration has a conservative global limit of 30/hour, login 10/email/15 minutes, SMS 1/account/minute and 5/account/day (100 globally/day); tune these with operational monitoring before a public launch.

## Checks

`pnpm test` covers auction/OCR rules, catalog parity/interpolation, combined search filters, sorting, MFK boundaries and mutation origin checks. `pnpm typecheck` and `pnpm build` validate source and production routes. `pnpm format` formats source files.

`pnpm test:integration` migrates and tests the isolated `_test` database using real PostgreSQL and injected payment/SMS simulators. It verifies registration restrictions, SMS replay/rate limits, identity RBAC, listing creation, concurrent bids, anti-sniping, pending/foreign/expired holds, idempotency, release retries, webhook signatures/ordering, renewal and abandoned checkouts. No simulator can be enabled through a production environment variable or HTTP request.

`pnpm test:settlement` covers no-bid/reserve outcomes, duplicate closers and seller decisions, deadline rechecks, unauthorized actions, completed-sale captures, lost provider responses, default review/dismissal/compensation, cancellation, expired-hold renewal after closing, retries and webhook recovery. Use the same isolated database configuration as the integration suite; run database suites sequentially.

After `pnpm build`, `pnpm test:http` starts a temporary production server on port 3100 against the isolated test database. It checks registration/login cookies, role guards, missing-provider failures, photo upload, identity approval, listing creation/review and masked public data. Test-only fixtures stand in for external SMS and identity evidence. It stops its server and removes its account/listing/photo fixtures. Both suites refuse database names that do not end in `_test`. Local defaults target `autoveri_test`; otherwise set TEST_DATABASE_URL explicitly. No real SMS or card charge is performed by either suite.

Production startup requires NODE_ENV=production, NEXTAUTH_URL, NEXTAUTH_SECRET, DATABASE_URL and durable UPLOAD_DIR. Run `pnpm build`, then `pnpm start`. Keep the custom server running. Next.js 14 is retained from the requested stack; review supported versions and dependency security updates before deployment.
